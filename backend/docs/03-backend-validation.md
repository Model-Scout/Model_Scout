- clarify/reject/후보 없음, 요청 검증, 429 및 CORS 응답 헤더.
- AI 스트림 done 누락, 저장 실패, 중복 실행 lease 정리.
- 원문 경로 검증·응답 잘림, SSE 다중 data 행·종료 구분자 처리.
- 실제 LangGraph와 clarify 노드로 되묻기 재개 시 새 plan이 전달되어 answer로 끝나는지 검증(LLM·검색은 대역).
- 실제 백엔드·AI 서버·LangGraph를 HTTP로 연결해 느린 노드 도중 취소 후 같은 그룹 재요청: 실행 겹침 없음, 취소된 실행은 끝까지 가지 않고(assess·explain 미진입) 닫힘, 최종 체크포인트는 재요청 결과(노드 내용·체크포인터는 대역).
- 내부 설명 질문 모듈이 전달받은 스냅샷을 LLM 요청에 넣고 token/done/error를 생성하는지 검증.
- mock 예시를 실제 Pydantic 모델로 검증.

**DB 테스트는 SQLite 기반 저장소 대역이고, AI SSE·LLM 호출은 테스트 대역이다.**
실제 PostgreSQL 드라이버·권한·네트워크, LangGraph 실행, 실제 LLM의 답변 품질을 검증한 결과가 아니다.
Windows에서는 샌드박스 안팎 모두 소켓 오류 WinError 10014로 테스트가 간헐적으로 실패했다. 프로젝트 코드 없이 이벤트 루프만 만들어도 재현되며, Linux에서는 발생하지 않았다.

## 운영 연결 전 확인

1. 대상 DB에 app_schema.sql 적용. 기존 메시지 보존·sources 컬럼·시퀀스 권한 확인.
2. 백엔드 DB 환경변수·AI_URL을 설정하고 AI와 백엔드를 함께 실행.
3. 새 세션으로 실제 추천 → 필요 시 clarify 답변 → 모델·데이터셋·최종 done 도착 확인.
4. 같은 그룹에서 question → result=null, 설명 답변·근거 저장 확인.
5. 조건을 바꾼 recommend → 새 추천 저장 → 새로고침·공유 링크에서 최신 결과와 메시지 확인.
6. 재시작 후 복원, 다른 세션의 쓰기 403, 원문 마운트·kind별 조회 확인.
7. Caddy를 거친 SSE 즉시 전달, 프론트 운영 도메인 CORS, 취소·장시간 연결·동시 부하 확인.

운영 DB 변경, VPS 배포, 실제 LLM 유료 호출, 프론트 코드 변경, 팀원에게 메시지 전송은 이번 로컬 작업에서 하지 않았다.

## 구현 한계·정책

- 같은 그룹 중복 실행 방지는 프로세스 내 상태다. 워커·인스턴스를 늘리려면 DB 잠금 등으로 바꿔야 한다.
- 취소는 즉시 중단이 아니다. 실행 중인 노드와 그 안의 LLM 호출은 끝까지 돌고, 취소를 감지하기 전 다음 노드가 하나 더 시작될 수 있다.
- 취소된 실행의 중간 상태는 체크포인트에 남아, 같은 그룹의 다음 recommend가 그 plan을 이어받을 수 있다.
- 취소된 사용자 메시지는 답변 없이 기록에 남는다.
- 요청 멱등 키·실행 재개·별도 run 상태 조회는 없다. 네트워크 단절 후 자동 재전송하지 않는다.
- 저장된 인용·결과는 스냅샷이지만 전체 README는 현재 파일을 조회한다.
- 공개 링크는 전체 대화를 공개하며 만료·철회가 없다. 일반 사용자 계정 기반 접근 제어는 MVP 밖이다.
- 언어·실행 환경 검증 근거는 현재 AI 출력에 없어 unknown이다. 추후 AI가 구조화된 근거를 제공하면 어댑터에서 반영한다.
- 공유된 과거 체크포인트가 AI 보존 정책으로 삭제됐다면 recommend는 이전 AI 계획을 이어가지 못할 수 있다. question은 app 스냅샷으로 동작한다.
- 프론트는 기존 /api/recommend 계약에서 이 명세로 별도 전환해야 한다. 기존 화면이 자동으로 연동되는 변경은 아니다.
