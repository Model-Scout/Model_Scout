# Model Scout 최종 검색 성능 (2026-11-27)

지금 서비스 설정 그대로 모델 검색과 공공데이터 검색의 성능을 골든셋으로 잰 결과다. 운영 코드·DB·배포는 바꾸지 않았다(Supabase 읽기 전용, OpenAI 호출만).

## 요약

| | 모델 검색 | 공공데이터 검색 |
|---|---:|---:|
| 상위 3개 안에 **쓸 만한** 결과가 있는 비율 (Hit@3, 1점 이상) | **90.6%** | **97.2%** |
| 상위 3개 안에 **딱 맞는** 결과가 있는 비율 (Hit@3, 2점) | 65.6% | **97.7%** |
| 상위 5개 안에 딱 맞는 결과가 있는 비율 (Hit@5, 2점) | 75.0% | **100%** |
| MRR@10 (쓸 만한 결과 기준) | **0.841** | **0.956** |
| Recall@5 (쓸 만한 결과 기준) | 0.611 | 0.764 |
| nDCG@5 | 0.487 | 0.813 |

- **모델 검색:** 서비스는 역할(임베딩·LLM·분류 등)마다 모델 3개를 보여 준다. 그 3개 안에 쓸 만한 모델이 있었던 역할이 90.6%다. 수치는 planner 가 검색까지 보낸 역할 32개 기준이다([한계](#한계) 1번).
- **공공데이터 검색:** 서비스는 6개를 보여 준다. 질문에 딱 맞는 데이터가 상위 5개 안에 100% 들어 있었고, 첫 정답은 평균 1위 근처(MRR 0.944, 딱 맞는 결과 기준)에 있었다.

## 무엇을 쟀나

| | 모델 검색 | 공공데이터 검색 |
|---|---|---|
| 골든셋 | **새로 만든 프로젝트형 30문항**("~ 프로젝트를 하려는데 모델만 추천해줘"), 정답 역할 43개 | 기존 공공데이터 골든셋 v2(코퍼스 `aa1a71d35a121150`, 라벨 v9)의 추천 질문 53개 |
| 정답 | 역할마다 코퍼스 4,017개를 전수 스캔해 0/1/2점(`model_retrieval/tools/scan.py` 규칙) | 카드 기반 LLM 판정 0/1/2점(기존 라벨 그대로) |
| 서비스 설정 | project 경로(`PROJECT_MODEL_SEARCH`: dense 0.9, IDF sparse, 리랭크 꺼짐) | 하이브리드 검색 + LLM 리랭크(`dataset_rerank`, gpt-4.1-mini, 상위 20개) |
| 실행 | 질문마다 라우터 → planner → 검색을 운영 코드 그대로 실행 | 같음. 리랭크는 2회 평균 |

점수 기준:
- **2점(딱 맞음):** 그 일을 하라고 만든 모델·데이터다. 모델은 한국어 전용이고 카드에 그 능력이 명시돼 있어야 한다.
- **1점(쓸 만함):** 쓸 수는 있다. 다국어 범용 모델, 양자화 변환본, 전국 데이터 안에 해당 지역이 포함된 경우 등이다.
- **0점:** 판정되지 않은 결과도 0점이다.

## 지표

| 지표 | 뜻 |
|---|---|
| Hit@k | 상위 k 개 안에 정답이 하나라도 있는 비율. 사용자가 화면에서 쓸 것을 찾는지 |
| MRR@10 | 상위 10개 안 첫 정답 순위의 역수 평균. 1이면 늘 1위, 0.5면 평균 2위 |
| Recall@k | 상위 k 개에 든 정답 수 ÷ min(k, 정답 수). k 칸을 정답으로 얼마나 채웠는지 |
| Precision@k | 상위 k 개 중 정답 비율 |
| nDCG@k | 2점·1점과 순위를 함께 본 점수. 이상적인 순서면 1 |

Recall 분모를 min(k, 정답 수)로 둔 이유가 있다. 한국어 LLM 처럼 정답이 수백 개인 역할에서는 일반 recall 의 최댓값이 0에 가까워져 비교가 안 된다.

## 참고: 리랭커 효과

같은 후보 20개를 리랭커 없이 줄 세운 순서와 비교했다. 95% 구간은 부트스트랩 값이고, 구간이 0을 포함하면 우연일 수 있다.

| | 지표 | 리랭크 없음 | 리랭크 | 차이 (95% 구간) |
|---|---|---:|---:|---|
| 공공데이터 (운영에서 켜져 있음) | MRR@10, 2점 | 0.644 | 0.944 | **+30.0%p** [+19.6, +41.0] |
| | nDCG@5 | 0.611 | 0.813 | **+20.2%p** [+12.8, +28.1] |
| | Hit@3, 2점 | 0.791 | 0.977 | **+18.6%p** [+7.0, +30.2] |
| 모델 (project 경로에서는 꺼져 있음) | Recall@5, 1점 이상 | 0.611 | 0.677 | +6.6%p [+0.8, +12.8] |
| | nDCG@5 | 0.487 | 0.533 | +4.5%p [−2.9, +11.9] |
| | MRR@10, 2점 | 0.604 | 0.606 | +0.2%p [−14.1, +13.7] |

- 공공데이터 리랭커는 모든 지표에서 확실하게 성능을 올린다.
- 모델 리랭커는 오르는 방향이지만 30문항으로는 확정되지 않는다.
- 리랭커 질문에 역할 설명을 붙인 변형도 재 봤는데, 더 나빠서 버렸다.

## 모델 Recall 이 공공데이터보다 낮은 이유

역할별 상위 결과를 직접 확인해 원인을 나눴다.

1. **planner 가 역할을 빠뜨린다.** 역할 43개 중 11개는 검색이 시작되지도 않았다. 가장 큰 원인이다.
   - QA 챗봇 3문항(pj06·24·29)은 임베딩+LLM 이 `question_answering` 하나로 합쳐졌다. 이 태그가 붙은 모델은 코퍼스에 29개뿐이다.
   - RAG·검색 질문 4개에서 reranker 역할이 만들어지지 않았다.
   - 통역 앱(pj26)에서 음성인식 역할이 빠졌다.
2. **정답 규칙이 엄격하다.** 카드에 그 능력이 글자로 적힌 모델만 정답으로 인정한다. 게임 NPC(pj16)에서는 한국어 대화 모델이 나왔지만, 카드에 "롤플레이"라는 말이 없어 0점이 됐다. 그래서 실제 체감보다 낮게 잡힌다.
3. **딱 맞는 모델이 적다.** 역할에 따라 2점 모델이 1~14개뿐이고 한국어 전용 조건까지 붙는다. 그래서 상위 5칸을 2점으로 채우기 어렵다.
4. **검색어에 핵심 단어가 빠진다.** AI 에이전트(pj20)에서 planner 의 검색어에 "function calling / tool"이 없어 도구 호출 모델을 찾지 못했다.
5. **task 매핑이 어긋난다.** 표·차트(pj17)의 정답은 비전 모델인데, `table_qa` 는 LLM 쪽으로 검색된다.
6. **양자화 재포장본이 상위 칸을 차지한다.** 번역(pj09)은 상위 5개 중 4개가 같은 모델 2개의 GGUF 재포장본이었다.

개선 여지는 검색 가중치나 리랭커보다 planner 의 역할 분해(1·4·5번)와 재포장본 묶기(6번)에 크다.

## 한계

1. **모델 요약 수치는 검색된 역할 기준이다.** planner 가 만들지 않은 역할 11개까지 0점으로 넣으면 Hit@3(1점 이상)가 90.6%에서 73.9%로 내려간다(질문 단위).
2. **"모델만 추천해줘" 30문항 중 17개를 planner 가 `recommend=false`(직접 질문)로 판단했다.** 운영에서는 이 질문들이 유형 분류 경로로 간다. 이 측정은 30문항 모두 project 경로로 고정했다.
3. **정답 판정이 자동이다.**
   - 모델 정답은 정규식 스캔이고 사람이 검수하지 않았다. README 원문에만 근거가 있는 모델은 1점으로 셌다.
   - 공공데이터 라벨은 리랭커와 같은 카드를 읽은 LLM 판정이다. 그래서 리랭크 쪽에 유리하게 기울 수 있다.
4. **질문 수가 적다.** 모델 30문항, 공공데이터 53문항이고 모두 첫 턴만 쟀다.
5. 공공데이터 사본(v2 그래프의 duplicates)은 하나로 센다.
