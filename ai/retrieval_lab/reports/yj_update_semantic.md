# semantic_capability 재채점 · 재정렬 실험 · 라벨 재판정 준비

작성 2026-11-01 · 예주 · 앞선 실험은 [`yj_summary.md`](yj_summary.md)

**한 줄 요약.** semantic_capability의 Recall@10 0.373은 후하게 매긴 1점 라벨 때문에 부풀려진 값이다. 확실한 정답(2점)만 세면 top-10에 정답이 하나도 없는 질의가 37개 중 8개다. LLM 없이 소프트 조건과 인기도로 재정렬하면 2점 기준 Recall@10이 0.365에서 0.409로 오른다. 다만 planner에 반영하려면 라벨 재판정과 지표 기준을 먼저 정해야 한다(6장).

## 1. 지금까지 한 것 (요약)

| 유형 | 질의 | planner 설정 | Recall@10 (Baseline → 최종) | 비고 |
|---|---:|---|---|---|
| model_comparison | 21 | Name Lookup, dense 0.5, LLM 없음 | 0.714 → 1.000 | 질문 속 모델명을 DB에서 바로 찾아 맨 앞에 고정 |
| semantic_capability | 37 | Decomposition + Multi-Query, dense 0.75 | 0.318 → 0.373 | 보완 라벨 1,358건(Claude 1차 판정) 포함 |

두 수치 모두 그대로 믿기 어렵다.

- **model_comparison 1.0**: 질의마다 정답이 2개이고 둘 다 질문에 이름이 그대로 적혀 있다. 게다가 Name Lookup 규칙을 이 21개 질의를 보고 만들었다. 표기 변형("엑사원 3.5", "whisper large v3")이나 일부만 쓴 이름에서의 성능은 아직 모른다.
- **semantic_capability 0.373**: 질의당 관련 모델이 평균 24.7개(2점 7.2 + 1점 17.5)라 Recall@10의 상한이 평균 0.571이다. 그리고 아래 2장처럼 1점 라벨이 후하다.

## 2. 2점 기준으로 다시 채점

검색 결과는 그대로 두고 채점 기준만 바꿨다. `min_grade=2`이면 2점만 정답으로 센다. 이 기준에서는 Recall@10의 상한이 0.923이다.

| 설정 | Recall@10 (1점 이상) | **Recall@10 (2점만)** | **Hit@10 (2점만)** | nDCG@10 |
|---|---:|---:|---:|---:|
| Baseline (dense 0.5) | 0.318 | 0.366 | 0.757 | 0.514 |
| 현재 planner (Decomp+MQ, dense 0.75) | 0.373 | 0.396 | 0.784 | 0.539 |

37개 질의 중 8개는 top-10에 2점 모델이 없고, 그중 6개는 top-30에도 없다. 그런데 1점 기준으로 세면 같은 질의들의 P@10이 0.7~1.0으로 나온다. top-10을 채운 모델들을 열어 보면 판정 이유에 위반이 적혀 있는데도 1점이었다.

| 질의 | 2점 정답의 실제 순위 | top-10을 채운 모델과 Claude 판정 이유 (1점) |
|---|---|---|
| g007 GPU 없는 PC에서 1시간 회의 전사 | 33 · 117 · 219위 | "4B라 CPU에선 느림", "1.5B라 CPU에서 느림" |
| g020 맥용, 속도 우선 전사 | 31 · 69 · 151위 | Voxtral 4B 복사본 5개, "4B로 무거움" |
| h023 PDF를 마크다운으로 바꾸는 파서 | 45~161위 | 27B 범용 VLM GGUF들, "전용 파서 아님" |
| h028 메신저 캡처 정리, 로컬 실행 | 77~286위 | TheCluster의 Qwen MLX 변종 9개 |
| g024 Jetson용 작은 한국어 임베딩 | 27~200위 | 다국어 0.6B 모델들, "한국어 특화 아님" |

라벨 구성도 세어 봤다.

- 관련 라벨 915개 중 737개(80%)가 Claude 판정이다.
- Claude가 준 1점 570개 중 318개(56%)는 판정 이유에 "무거움, 느림, 아님, 불명확, 부족" 같은 위반이나 불확실 표현이 있다.

결론이 바뀌지는 않았다. 2점 기준에서도 현재 planner 설정이 Baseline보다 낫다. 다만 Hit@10 차이는 질의 1개 수준이다. 가중치 곡선도 들쭉날쭉해서(dense 0.6은 0.343, 0.75는 0.396) 0.75라는 값은 노이즈에 가깝다.

## 3. 검색 개선 실험: 후보 확대와 소프트 조건

RRF 결과 상위 D개를 다시 정렬했다. 점수는 `RRF 점수(1위=1.0으로 정규화) + λ_soft × 소프트 조건 + λ_pop × 인기도`다.

- **소프트 조건**: 질의문 키워드로 판단하는 일반 규칙이다. 질의별로 맞춘 규칙이 아니다.
  - 경량("GPU 없음, CPU, 가볍게, Jetson, 온디바이스, 휴대폰, 속도"): 1B 이하 +1, 3B 이하 +0.5, 3~7B −0.5, 7B 이상 −1, 양자화(GGUF/ONNX 등)면 +0.5. 단 "GPU 서버"나 "큰 GPU"가 있으면 경량 조건을 끈다.
  - 맥: MLX, CoreML, MPS가 문서화된 모델 +1
  - 양자화 요청: 양자화 모델 +1
  - 37개 질의 중 8개에 소프트 조건이 걸린다.
- **인기도**: log10(downloads + 1) / 7
- **변종 묶기**: 같은 `canonical_model_id`는 가장 높은 것 하나만 제자리에 남긴다.
- **후보 확대**: 채널별 후보를 100개에서 300개로 늘리고, 재정렬할 범위 D를 30, 100, 300으로 바꿔 봤다.
- 가중치는 **2-fold 교차검증**으로 골랐다. 질의를 짝수와 홀수로 나눠 한쪽에서 고르고 다른 쪽에서 쟀다.

| 설정 | Recall@10 (2점만) | Hit@10 (2점만) | nDCG@10 |
|---|---:|---:|---:|
| Baseline | 0.365 | 0.730 | 0.512 |
| Baseline + 재정렬 (교차검증) | **0.409** | 0.784 | 0.535 |
| Decomp+MQ, dense 0.75 (현재 planner) | 0.384 | 0.757 | 0.540 |
| Decomp+MQ + 재정렬 (교차검증) | **0.434** | 0.784 | **0.593** |

채널 깊이 300 조건에서 다시 잰 값이라 2장 표와 소수점이 조금 다르다.

요소별로 하나씩만 켜 본 결과는 이렇다.

- **후보 확대는 효과가 없었다.** 교차검증에서 매번 D=30이 뽑혔다. 키워드와 인기도 같은 약한 신호로는 100위 밖의 정답을 끌어올리지 못하고 노이즈만 같이 올라온다.
- **소프트 조건**은 Recall@10(2점)을 +0.013~0.026 올렸다.
  - 고친 질의: h065 "GPU 없이 다국어 QA"(0 → 1.0), g020 "맥용 전사"(0 → 0.67), h060 "CPU 서버 요약"(0.50 → 0.83)
  - 못 고친 질의: g007, g024. 정답이 33위 이하에 있다.
  - 오히려 나빠진 질의: g023. 질의에 "0.6B급은 품질이 부족했다"고 적혀 있는데 경량 규칙이 작은 모델을 올렸다.
- **인기도**는 소프트 조건이 없는 질의에서도 도움이 됐다(h041, h056, h058). Decomp+MQ에서는 가장 큰 기여 요소였다.
- **변종 묶기**는 효과가 섞여 있어서 교차검증에서 대부분 꺼졌다.

해석할 때 주의할 점이 넷 있다.

1. **LLM 없는 Baseline + 재정렬(0.409)이 현재 LLM 설정(0.384)보다 높다.** nDCG는 비슷하고, p95는 약 0.7초로 LLM 설정의 약 5.2초보다 훨씬 빠르다.
2. 이득은 질의 1~2개 수준이다. Recall이 오른 질의는 9~10개, 내린 질의는 3~4개다. Baseline 쪽은 교차검증에서 뽑힌 가중치가 fold마다 달라 불안정하다.
3. **인기도 이득의 일부는 라벨 편향일 수 있다.** 희원님 structured 검증에서 Claude 판정에 "인기도·공식성 가점" 편향이 지적됐다(9건).
4. 정답이 30위 밖에 있는 질의(g007, g024, h023, h028)는 휴리스틱으로 못 푼다. 후보를 넓히려면 cross-encoder Reranker처럼 강한 신호가 필요하다.

## 4. 라벨 재판정 워크시트

`python -m retrieval_lab.semantic_worksheet`를 실행하면 `test/golden/labels/worksheet_semantic_capability.jsonl`이 만들어진다. 대상은 판정 이유에 위반이나 불확실 표현이 있는 Claude 1점 판정 318건이고, 25개 질의에 걸쳐 있다.

| 갈래 | 판정 이유의 표현 | 다시 볼 질문 | 전체 | top-10 안 |
|---|---|---|---:|---:|
| size_speed | 무거움 · 느림 | 질의가 경량을 요구했다면 위반이니 0점 후보 | 37 | 14 |
| not_specialized | ~특화 아님 | 범용 모델로 할 수는 있다. 1점과 0점의 경계 | 241 | 77 |
| no_evidence | 불명 · 부족 · 않음 | 카드가 침묵한다. 점수 대신 보류(unjudged) 후보 | 40 | 13 |

- 지표에 바로 영향을 주는 top-10 안의 104건이 파일 앞쪽에 정렬돼 있다.
- 행마다 질의문, 이전 판정 이유, 메타데이터(task, 파라미터 수, 양자화, canonical, 다운로드), `readme_path`가 들어 있다.
- 규칙이 0점을 제안하는 것은 "경량 질의 + 4B 이상이 확인된 모델" 5건뿐이다. 나머지는 사람이 정한다.
- 점수는 0, 1, 2, "unjudged" 중 하나를 적는다. **판정 전에 README를 반드시 연다.** lexical·structured 검증에서 오류의 주원인이 README 미확인이었다.

## 5. 다음 순서 (제안)

1. 워크시트 318건을 재판정한다. 우선 top-10 안의 104건부터 한다.
2. 재판정 라벨로 2장(재채점)과 3장(재정렬)을 다시 돌린다. 인기도 이득이 남는지 함께 확인한다.
3. 이득이 남으면 `pipeline.run`에 재정렬 단계를 넣고 planner에 `rerank` 필드를 추가한다. 공유 코드라 리뷰가 필요하다.
4. Reranker(top-100 cross-encoder)를 따로 실험한다.
5. model_comparison에 어려운 질의 10~15개를 평가 전용으로 추가한다.

## 6. 의논할 것

| # | 안건 | 제안 | 결정 |
|---:|---|---|---|
| 1 | 대표 지표 | 정답 수가 질의마다 크게 다른 유형은 Recall@10(1점 이상) 대신 **2점 기준 Recall@10 + Hit@10 + nDCG@10**을 본다. 모든 유형에 같은 기준을 쓸지 정해야 한다 | |
| 2 | "특화 아님" 범용 모델의 점수 | 질의가 특정 도메인이나 용도를 요구하면 0점, 그렇지 않으면 1점. 241건이 이 기준에 달려 있다 | |
| 3 | 판정 보류(unjudged) 버킷 | 카드가 조건에 침묵하면 1점이 아니라 보류로 뺀다. 희원님 structured 노트에서도 같은 제안이 나왔다. 골든셋 원본에는 이미 `unjudged`가 있다 | |
| 4 | 재판정 담당과 분량 | 318건 중 top-10 안의 104건을 먼저 하고 나눠서 판정한다. Claude 판정은 사람이 검수한 뒤에만 반영한다 | |
| 5 | 평가 전용(held-out) 질의 | 가중치와 규칙을 고른 질의로 평가하지 않는다. 새 질의 일부를 튜닝에서 빼는 것을 팀 공통 규칙으로 한다 | |
| 6 | LLM 사전 검색 유지 여부 | semantic_capability는 LLM 없이 재정렬한 설정이 현재 LLM 설정과 같거나 낫고 7배 빠르다. 재판정 뒤 다시 비교해 정한다 | |
| 7 | 재정렬 단계를 공유 파이프라인에 넣을지 | planner 필드(`use_rerank`, `soft_weight`, `pop_weight`)로 넣고, 유형별 옵트인으로 한다 | |
| 8 | 인기도 가점 | 라벨 편향과 신규 모델 불리 문제가 있다. 넣는다면 상한(λ_pop ≤ 0.2)과 재판정 후 재검증을 조건으로 한다 | |
