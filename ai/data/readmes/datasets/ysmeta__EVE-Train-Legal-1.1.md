# EVE-Train-Legal-1.1

Supersedes [EVE-Train-Legal-1.0](https://huggingface.co/datasets/ysmeta/EVE-Train-Legal-1.0),
adding `verified_negatives.jsonl`. The 134,996 pairs are byte-identical to 1.0.

Training pairs for Korean legal precedent retrieval: **134,996 (query, precedent)**
pairs plus **19,038 queries with verified hard negatives**, used to train
[ysmeta/EVE-Embed-1.1-Legal](https://huggingface.co/ysmeta/EVE-Embed-1.1-Legal)
(+12.8% nDCG@10 over its base model).

Queries are written the way a practitioner asks, not the way a court writes.

## Contents

| file | rows | description |
|---|---|---|
| `train.jsonl` | 134,996 | flat (query, positive) pairs, ready for contrastive training |
| `train_synth_raw.jsonl` | 45,000 | one row per precedent, all 3 queries grouped + original 판시사항 |
| `verified_negatives.jsonl` | 19,038 | queries with LLM-verified hard negatives (avg 3.9 each) |

```python
{"query": "계약금을 이미 받았는데도 상대방이 계약 취소할 수 있나요?",
 "positive": "소유권이전등기청구사건 당사자의 일방이 계약이행에 착수한 후에는 …",
 "negatives": []}
```

`negatives` is empty in `train.jsonl` — the usable negatives live in the separate
file, for the reason below.

## Mined hard negatives are 32.4% false negatives — measure before you use them

The obvious recipe is to mine hard negatives with a strong retriever. Done naively in
this domain it **actively hurts**:

| configuration | nDCG@10 | vs base |
|---|---|---|
| mined hard negatives, skip top-3, lr 2e-5 | 0.4434 | −36.5% |
| mined hard negatives, skip top-10, lr 5e-6 | 0.6457 | −7.5% |
| no mined negatives, in-batch only | 0.7800 | +11.7% |
| **+ LLM-verified negatives** | **0.7872** | **+12.8%** |

Legal precedents cluster tightly by issue, so the highest-ranked non-gold documents for
a legal question are usually *genuinely relevant* cases with a different holding.
[Tencent Hy3](https://huggingface.co/tencent/Hy3) judged 20,000 queries against their
top-10 mined candidates and found **64,741 of 200,000 (32.4%) genuinely answer the
query**. Training against those teaches the model that correct answers are wrong.

Skipping the top 10 hits does not fix it — the false negatives run deeper than that.
Judging each candidate does: `verified_negatives.jsonl` is what survived, and adding it
is worth +0.0072 nDCG@10 over in-batch negatives alone (paired bootstrap 95% CI
[+0.0046, +0.0099], p < 0.0001).

Verification is cheap next to the downside: one LLM call per query listing all 10
candidates at once, ~5 queries/sec, 68 minutes for 20,000. Per-pair calls would have
been ~1M requests.

Whether or not you use them, run `MultipleNegativesRankingLoss` with the **largest
batch you can afford** — batch size is the in-batch negative count, and those negatives
are safe. Going from batch 64 to 512 was worth +1.1 points on its own.

## Construction

1. 45,000 precedents from [joonhok-exo-ai/korean_law_open_data_precedents](https://huggingface.co/datasets/joonhok-exo-ai/korean_law_open_data_precedents)
   (Korean government open data), restricted to cases carrying both 판시사항 and 판결요지.
2. Split by 사건번호 against [EVE-Bench-Legal-1.0](https://huggingface.co/datasets/ysmeta/EVE-Bench-Legal-1.0)
   so no case leaks between train and eval.
3. 3 queries per precedent generated by [Tencent Hy3](https://huggingface.co/tencent/Hy3)
   (Apache-2.0), prompted for plain practitioner phrasing from different angles.
4. `positive` is `사건명 + 판결요지`.

## Caveats

- Queries are **LLM-generated**. They imitate practitioner phrasing; real query logs
  would differ in distribution and messiness.
- Case types of the 45,000 source precedents: 민사 47.1% · 형사 21.1% ·
  일반행정 13.1% · 세무 12.8% · 특허 4.3% · 가사 1.5%.
- Finance appears as litigation, not as practice documents: 17.3% of the parent corpus
  names a financial institution or instrument (보험금, 약속어음금, 대여금,
  근저당권설정등기말소 …). 약관, disclosures and filings are not represented.
- 판례 only, no statute text (법령 조문).
